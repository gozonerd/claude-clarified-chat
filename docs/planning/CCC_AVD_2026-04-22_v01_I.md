## 2. System Shape

### 2.1 One-Paragraph System Description

Claude Clarified Chat is a local-only client-side application that ingests a user-provided Claude.ai thread export zip, parses its constituent JSONL + sub-agent transcripts + tool-results + metadata + logs into an in-memory typed event store, and renders that store through two output surfaces — an interactive timeline UI and a multi-format Clarity Corpus export (PDF/DOCX/XLSX/MD). The application performs all work on the user's machine with zero network calls at runtime; user data never leaves the device.

### 2.2 Architectural Style

| Style Axis | Choice | Rationale |
|---|---|---|
| Monolith vs. service | **Monolithic** (single deployment unit) | Single-user local app; services would violate local-only constraint |
| Client vs. server | **Client-side only** | No server component anywhere; local-only privacy constraint (TRD 3.4) |
| Sync vs. async | **Async event-driven** (ingest, parse, render, export) | Meets p95 ≤10s time-to-first-insight + streaming render budgets (TRD 3.1) |
| Stateful vs. stateless | **Stateless at rest** (per-session in-memory only; user owns persistence) | Zero retention per TRD 3.4; user controls all persistence via OS file operations |
| Form factor | **Deferred** (web static OR desktop installer) | Open question Q-001 / TQ-001 — Stage 00 Track 1 decides; architecture below is form-factor-agnostic until Stage 00 resolves |

### 2.3 Surface Layers

| Surface | Consumer | Relationship |
|---|---|---|
| Primary UI | Human user via browser or desktop window | Top-level surface; all interactive flows live here |
| Exported Clarity Corpus | Human user (post-export) + downstream tools (PDF reader, Word/Docs, Excel, Markdown renderer) | Generated artifact; one-way output from the UI |
| Local audit log (ingest/export events) | Human user (introspection only) | Side channel; never transmitted; user-controlled retention per TRD 3.8 |

No API surface. No developer-facing surface. No SDK surface. Per PRD Section 3.3 non-goals.

## 3. Components And Boundaries

### 3.1 Component Inventory

| Component | Responsibility (one sentence) | Inputs | Outputs | Public Interface |
|---|---|---|---|---|
| **Ingest Adapter** | Accept a user-provided zip, validate its structure, and make the extracted contents available to the Parser Engine. | Zip file path (from drag-drop or file-picker) | In-memory file map keyed by relative path | `ingest(zip: File) → Promise<FileMap>` |
| **Parser Engine** | Parse JSONL + sub-agent transcripts + tool-results + metadata + logs into typed entities. | FileMap from Ingest Adapter | Populated Event Store | `parse(files: FileMap) → Promise<EventStore>` |
| **Event Store** | Hold typed entities in memory with indexed access by id, type, timestamp, and sub-agent association. | Entities from Parser Engine | Queries from renderers + export + token accounting | `query(filter: Filter) → Event[]`; `get(id: string) → Event` |
| **Token Accounting Engine** | Derive a TokenAttribution waterfall across main thread + sub-agents + tool uses. | Event Store | Structured waterfall entity | `computeWaterfall(store: EventStore) → Waterfall` |
| **Secret Pattern Detector** | Scan event content for secret patterns (API keys, JWT, credentials). | Event content | List of detected patterns with location + severity | `scan(events: Event[]) → Detection[]` |
| **Timeline Renderer** | Render the chronological event stream with filter + search affordances. | Event Store queries | DOM / native UI tree | Component API specific to framework chosen Stage 00 |
| **Detail View Renderer** | Render full content of a single selected event. | Event via Event Store `get()` | DOM / native UI tree | Component API |
| **Export Engine** | Produce the Clarity Corpus in PDF / DOCX / XLSX / MD, running all four in parallel. | Event Store + Waterfall + user-chosen output paths | Four artifact files | `export(targets: FormatTarget[]) → Promise<ExportResult>` |
| **Accessibility Layer** | Provide ARIA live regions, keyboard-navigation harness, `prefers-reduced-motion` handling, focus-indicator engine, and cognitive-accessibility navigation guarantees. | UI events, OS media-query changes | Announcements + focus-state changes | Mixin / provider API applied across all UI components |
| **Local Audit Logger** | Write local-only structured log entries for ingest and export events. | Lifecycle events | Local log file at user-controlled path | `log(event: AuditEvent) → void` |
| **UI Shell** | Routing, layout, theming, top-level state orchestration. | User navigation actions | View selection + theming context | Framework-specific |

### 3.2 Boundaries

| Boundary Type | Where It Sits | What It Protects |
|---|---|---|
| Process boundary | Single process at MVP | No IPC surface to attack |
| Language / runtime boundary | **Conditional:** if Tauri desktop chosen, Rust (Parser Engine + Ingest Adapter) vs. TypeScript (UI + renderers); if web chosen, single-language TypeScript. Decided Stage 00. | Native-vs-web-side responsibility split |
| Trust boundary | User-provided content (Thread zip) is UNTRUSTED on the parser side; TREATED as data, never executed | Prevents dynamic code execution on user content (TRD 6.2) |
| Filesystem boundary | Zip extraction sandboxed to memory or app-scoped temp dir purged on close (TRD SR-001) | Prevents zip-slip; prevents leak of user content to other apps |
| Release boundary | Single release unit (one version of the whole app ships at a time) | Simplifies Stage 02 scaffold; matches solo-operator constraint |

## 4. Data Flow

### 4.1 Primary Data Flows

**Flow F1 — Ingest → Timeline (PRD Journey J1):**

1. User drops zip → UI Shell dispatches to Ingest Adapter
2. Ingest Adapter validates (zip-slip guard, zip-bomb guard, required-structure check) → extracts to sandboxed memory/temp → yields FileMap
3. FileMap → Parser Engine parses each constituent file type → yields typed entities
4. Entities → Event Store populates with indexes (by id, type, timestamp, sub-agent)
5. Parser emits progress events → Accessibility Layer announces via ARIA live region; Timeline Renderer subscribes to store and renders incrementally
6. Token Accounting Engine derives waterfall off the populated store (async, concurrent with timeline render)
7. Audit Logger writes ingest event
- Latency (TRD 3.1): p50 ≤ 5s, p95 ≤ 10s for 300-line JSONL

**Flow F2 — Detail View (PRD Journey J2):**

1. User clicks timeline event → Timeline Renderer emits selection event
2. UI Shell dispatches to Detail View Renderer with event id
3. Detail View Renderer calls Event Store `get(id)` → receives full event
4. Detail View renders full content with per-event-type layout (user msg / assistant msg / tool-use / tool-result / sub-agent spawn / thinking block / log entry)
- Latency: ≤ 50ms (in-memory lookup)

**Flow F3 — Export (PRD Journey J3):**

1. User triggers export from Corpus Preview modal
2. Secret Pattern Detector scans current Event Store for secret patterns
3. If detections: pre-export warning modal blocks until user acknowledges (TRD BR-005)
4. User acknowledges → Export Engine runs PDF + DOCX + XLSX + MD generators in parallel
5. Each generator writes to user-chosen local path via OS file-picker
6. Export Engine collects results, reports completion via Accessibility Layer announcement
7. Audit Logger writes export event with format list + paths
- Latency (TRD 3.1): p50 ≤ 30s, p95 ≤ 60s for all four in parallel on 300-line JSONL

### 4.2 Secondary Data Flows

**Flow S1 — Large-export streaming (TRD BR-002):**

Parser Engine parses in 100-line chunks; each chunk batch-inserts into Event Store; Timeline Renderer subscribes to store-change events and renders incrementally. UI remains responsive during parse (≥ 100 events per 200ms chunk).

**Flow S2 — Filter/search (TRD FR-008/009):**

User changes filter or search term → Timeline Renderer issues new query to Event Store → Store returns matching event subset (indexed lookup) → renderer updates view. Latency p95 ≤ 300ms for 10,000-event search.

**Flow S3 — Log panel (TRD FR-017):**

Separate panel subscribes to `LogEntry` entities in the store; renders timeline-correlated with the main event timeline.

### 4.3 Data Persistence Points

| Data | Persistence | Lifetime | Consistency |
|---|---|---|---|
| Parsed entities | In-memory only (Event Store) | Per session; discarded on app close | Strong (single-process, single-writer) |
| Export artifacts | User-chosen local filesystem path | User-controlled | N/A — one-shot write |
| Local audit log | User-controlled local filesystem path | User-controlled retention | Append-only with fsync-on-write |
| Source zip | Untouched (never modified) | User-controlled | N/A — read-only |

**No database. No cache. No remote persistence.**

## 6. Cross-Cutting Concerns

### 6.1 Logging And Observability

Structured JSON log entries with the following fields: `timestamp`, `event_type` (`ingest_start`, `ingest_complete`, `parse_error`, `export_start`, `export_complete`, `secret_detection`), `payload`. Written to user-controlled local log file. No remote observability. Cross-reference TRD Section 3.8.

### 6.2 Error Handling Strategy

**Result-type pattern** for parse errors (no thrown exceptions propagated to UI for expected failure modes). Expected failures:

- Single-event parse failure → `[unavailable]` marker entity added to store (TRD SR-002)
- Malformed zip → UI-level error boundary renders a friendly message with "what was readable" partial ingest if any
- Export path unwritable → UI-level error announced via Accessibility Layer; export marked failed for that format only; other formats continue

**Unexpected errors** (e.g., programming bugs) bubble to a top-level error boundary which: (a) preserves user data in Event Store, (b) announces via Accessibility Layer, (c) writes to local audit log, (d) never transmits.

### 6.3 Concurrency Model

- **Async/await** throughout ingest + parse + export pipelines
- Parser Engine parses in chunks concurrently with Timeline Renderer incremental render
- Export Engine runs 4 format generators in parallel (Promise.all equivalent)
- Secret Pattern Detector runs synchronously before export (must complete before warning modal)
- UI main thread protected from blocking: large parses offloaded (Web Worker if web, Tauri async task if desktop)

### 6.4 Security Architecture

Cross-reference TRD Section 3.3.

- **Input-validation boundary:** Ingest Adapter is the sole entry point for user content; validation happens there
- **No dynamic code execution** on user content (TRD 6.2)
- **Zip-slip prevention** in Ingest Adapter
- **Zip-bomb guard:** per-file decompression-size cap enforced
- **Dependency pinning + Stage QA audit** to mitigate supply-chain risk
- **No network calls at runtime** — enforced by CI test + static analysis

### 6.5 Accessibility Architecture

Accessibility is **architecturally enforced** via a dedicated Accessibility Layer component that wraps all UI components. This is a structural choice, not a feature. The Layer provides:

- ARIA live region for announcing state changes
- Keyboard-navigation harness enforcing focus order, visible focus indicators at ≥ 3:1 contrast, and keyboard shortcuts
- `prefers-reduced-motion` system-setting observer that disables or swaps animation
- Cognitive-accessibility navigation guarantees (≤ 2 navigation steps between any two views — enforced by a route-graph validator at build time)
- Screen-reader-first event announcements for async operations (ingest progress, export completion)

Cross-reference TRD Section 3.5 and TQCD Section 6.

## 7. Architectural Decisions (Mini-ADRs)

### AD-001 — Client-side monolith, no server

- **Status:** Accepted
- **Context:** TRD 3.4 data-sensitivity + TRD 6.1 local-only architecture require that no user data leaves the machine.
- **Options considered:** Client-server with user-run local server; client-side only; serverless-at-edge with end-to-end encryption.
- **Decision:** Client-side only. No server.
- **Rationale:** Any server component is an attack surface + complexity + compliance burden + hosting cost. Local-only is the simplest architecture that satisfies the privacy constraint absolutely.
- **Consequences:** Locks in: no multi-user features without architecture change; no remote observability; no server-side heavy computation. Forecloses: any feature that needs server state.

### AD-002 — Form-factor deferred to Stage 00

- **Status:** Deferred (decision pending)
- **Context:** TRD 6.3 platform target is "web or desktop", decided in Stage 00 Track 1 research.
- **Options considered:** Web static app; Tauri desktop; Electron desktop; PWA hybrid.
- **Decision:** Deferred. AVD is authored form-factor-agnostic; AD-002 becomes Accepted with the chosen option at Stage 00 boundary.
- **Rationale:** Premature commitment would foreclose valid options whose tradeoffs (bundle size, install friction, OS integration, accessibility APIs) are research-dependent.
- **Consequences:** Section 3.2 boundaries section notes conditional language-runtime boundary; Section 5.1 lists both candidates with separate runtime-environment tables.

### AD-003 — In-memory Event Store (no persistence)

- **Status:** Accepted
- **Context:** TRD 3.4 zero retention at the product layer.
- **Options considered:** In-memory only; local SQLite cache keyed by zip hash; IndexedDB (web) / file-backed cache (desktop) with user-controlled retention.
- **Decision:** In-memory only for MVP.
- **Rationale:** Zero retention rule forecloses default cache; user-controlled cache adds configuration surface + user-facing complexity that doesn't pay for itself at MVP scale (<=50k events fit easily in 500MB memory budget).
- **Consequences:** User re-ingests the same zip on each session — slow but acceptable given source-zip parse latency budget. Revisit if week-1 dogfood surfaces friction.

### AD-004 — Secret pattern detection runs pre-export only, not at ingest

- **Status:** Accepted
- **Context:** TRD FR-015 requires warning the user before secrets leave the product boundary.
- **Options considered:** Scan at ingest (warn on view); scan at export (warn before export artifact is written); scan continuously.
- **Decision:** Scan at export only.
- **Rationale:** Ingest latency budget is tight (p95 ≤ 10s); scanning adds cost. Secrets remaining on-device in the Event Store pose no additional risk beyond what the source zip already contains on disk. Risk materializes when content is transformed into a shareable artifact (export).
- **Consequences:** User cannot see detection warnings in the Timeline view. Documented as Known Compromise in Section 8.

### AD-005 — Parallel export generation

- **Status:** Accepted
- **Context:** TRD 3.1 Clarity Corpus export p95 ≤ 60s budget for 4 formats.
- **Options considered:** Sequential (PDF → DOCX → XLSX → MD); parallel with shared Event Store; parallel with event-store snapshot per worker.
- **Decision:** Parallel with shared in-memory Event Store (read-only access during export; no writers).
- **Rationale:** Sequential violates latency budget. Snapshot-per-worker doubles memory footprint. Shared-read access is safe because store is read-only during export phase.
- **Consequences:** Each exporter must be side-effect-free on the store. Store API restricts writes during export via a lifecycle flag.

### AD-006 — `[unavailable]` marker pattern for missing/unparseable data

- **Status:** Accepted
- **Context:** TRD SR-002 + FR-016: parse failures must never silently drop events.
- **Options considered:** Silent skip; abort whole ingest; marker entity + flag.
- **Decision:** Marker entity with `status: unavailable` and a `reason` field; flagged in timeline with a distinct visual indicator.
- **Rationale:** Forensic tool cannot have silent drops (would defeat the product's purpose). Aborting whole ingest is hostile to the user.
- **Consequences:** UI must visually distinguish `unavailable` events (per WCAG: not color alone); Clarity Corpus exports must render markers faithfully.

### AD-007 — No runtime network whatsoever

- **Status:** Accepted
- **Context:** TRD 6.1 mandatory constraint + PRD 6.3 privacy constraint.
- **Options considered:** Optional telemetry with user opt-in; optional update-check; strict no-network.
- **Decision:** Strict no-network. No opt-in, no update-check from within the app, no CDN, no external fonts, no external icons.
- **Rationale:** Opt-in telemetry opens an attack surface + compliance surface + still requires users to trust the opt-out. Strictly-no-network is simpler to verify and audit.
- **Consequences:** Updates distributed out-of-band (manual download). Font/icon assets bundled at build time (bundle-size cost).

### AD-008 — Accessibility enforced architecturally, not per-component

- **Status:** Accepted
- **Context:** PRD 6.4 + TRD 3.5 WCAG 2.1 AA + cognitive-accessibility specifics.
- **Options considered:** Per-component accessibility (each component handles its own); dedicated Accessibility Layer that wraps all components; accessible-by-default component library with opt-in overrides.
- **Decision:** Dedicated Accessibility Layer + accessible-by-default component library selected Stage 00.
- **Rationale:** Per-component ownership historically produces inconsistent accessibility. A structural Layer + library combination is the approach most likely to produce zero axe-core critical/serious violations by default.
- **Consequences:** Component library choice Stage 00 constrained to those that meet WCAG 2.1 AA without heroic effort. Route-graph validator needed at build time for the ≤-2-step navigation guarantee.
