# Product Requirements Document — Claude Clarified Chat

## 1. Product Identity

### 1.1 Product Name

**Claude Clarified Chat**

Part of the **Claude Clarified** product family. Sibling products (out of scope for this PRD): Claude Clarified Code (dev pipeline variant), Orchestra Metronome (real-time agent monitoring variant).

### 1.2 Version

**v0.1 MVP** — scoped for ship in 2026-Q2, matched to the D2R factorial-experiment cadence.

### 1.3 One-Line Description

A non-dev Claude user un-black-boxes a Claude thread export: what happened, when, why, and where the token budget went — in formats they can read, share, and cite.

---

## 2. Users And Problem

### 2.1 Primary Users

**Segment: Non-dev Claude.ai users with ADHD or similar cognitive-accessibility needs who run multiple simultaneous Claude threads and need to forensically audit what happened inside a thread without reading raw JSONL.**

- **Representative user:** Krystal (Columbia neuro BA, instructional designer, Martinez Methods operator). Runs 5+ Claude threads simultaneously. Uses Claude Code via the desktop app as a chat tool, not as a dev tool. Needs to audit sub-agent delegation and tool calls after-the-fact without reading JSONL.
- **What they do without this product:** either trust Claude's in-thread self-reports (unreliable — this session's 308-line JSONL included 6 sub-agents and a failure mode that was only partially visible in-chat), or manually attempt to open export zips and get overwhelmed.
- **What they struggle with:** sub-agent output buried in export zips; thinking blocks invisible during the chat; tool-use results that the main thread summarized possibly wrongly; no way to account for where token/time budget actually went.

### 2.2 Secondary Users

**Segment: Researchers and auditors studying LLM agent behavior who need structured, human-readable transcripts for analysis (AI safety, agent reliability research, regulatory compliance audits).**

Lower priority for MVP; named here so that output formats don't foreclose this use case.

### 2.3 Problem Statement

Non-dev Claude.ai users operate a fundamentally opaque system. Sub-agents, tool calls, thinking blocks, and hook execution happen invisibly. The in-chat summary is the agent's self-report, which is unreliable by construction — Claude may state it did X while the JSONL shows it did Y, or skipped Y, or delegated Y to a sub-agent whose output the main thread misrepresented. When a thread fails or produces bad output, the user has no forensic path to understand what actually happened.

**Evidence:**

1. **Direct experience in the export under test** — the 308-line session export includes 6 sub-agents (`a30ff6885e04365ae`, `a5d4faae5899168bd`, `a866e1246cb399945`, `a86fa0dc99e1f9822`, `aae475720c50acd5e`, `acompact-b4645bd2a68ca1d3`), buried tool results, and a documented failure mode around ableism/audience misreading. Chat surface showed task-notification stubs; actual sub-agent reasoning and thinking blocks were only in the JSONL.
2. **Burned token budget as a real cost** — user statement in the source session: *"you burned my tokens and usage. i am so broke i am deciding between food meds and gas."* Opacity-induced failure has direct financial cost borne by the user who had no way to see it going sideways in real time.
3. **Market gap articulated from need** — user statement in the source session: *"this is the ONLY tool on the market for non devs to understand claude's internal everything."* Independent market validation deferred to Stage 00 Track 3 benchmark research.
4. **Structural pattern across 5+ concurrent threads** — not one bad thread; a workflow where opacity is a throughput constraint.

### 2.4 Why Now

1. **Sub-agent orchestration went mainstream in 2026.** Claude Code's Agent tool, parallel sub-agents, skill-based delegation, hook orchestration became first-class. The gap between chat-surface and actual work widened structurally in the 2025→2026 transition.
2. **Non-dev users adopted Claude Code as a chat tool.** Pattern: *"using it in the desktop app and not as a techy cs or dev thing so we effectively chat."* Dev-oriented tool, non-dev users — recent and growing mismatch.
3. **Export format stabilized.** Session-export-*.zip schema (JSONL + subagents/ + tool-results/ + metadata.json + logs/) is stable enough in 2026 to parse against.
4. **Opus 4.7 / Sonnet 4.6 / Haiku 4.5 tokenizer overhead changes (2026).** Opus 4.7 carries ~35% per-call overhead vs. 4.6. Token cost is user-felt in a way earlier generations were cheap enough to ignore.
5. **AI reliability and accountability is a 2026 conversation.** EU AI Act applicability, NIST AI RMF, enterprise explainability demands. Market primed.

## 3. Goals

### 3.1 Primary Goals

| ID | Goal statement | Measurable criterion | Timeframe |
|---|---|---|---|
| G1 | User can locate what any sub-agent actually produced in a thread | ≤ 30 seconds from zip drop to reading a specific sub-agent's output, vs. baseline "unreachable without JSONL parsing" | Measured in week-1 dogfood post-MVP |
| G2 | User can answer "where did the token budget go" for any export | Waterfall view surfaces per-event token attribution across main thread + sub-agents + tool uses, summing to ≥ 99% of declared total | Measured on every export in week-1 dogfood |
| G3 | User can produce a shareable Clarity Corpus from any export | Export completes in ≤ 60 seconds for a 300-line JSONL to PDF + DOCX + XLSX + MD in parallel | Measured in automated tests on every build |
| G4 | Product operates at WCAG 2.1 AA | Zero axe-core `critical` or `serious` violations across all UI states | Measured in CI on every build |
| G5 | Primary user (Krystal) runs MVP against ≥ 5 existing threads within 7 days of ship and returns with ≥ 1 non-trivial finding per thread (sub-agent misbehavior, token drain, un-reported tool use, etc.) | 5 threads × ≥ 1 finding each = ≥ 5 findings logged | Measured at MVP + 7 days |

### 3.2 Secondary Goals

Nice-to-have; not required for MVP success:

- User generates and shares a Clarity Corpus with a third party (evidence that the shareable-artifact outcome clears the last-mile friction).
- Product usable by non-dev users outside primary user's circle with zero onboarding (evidence that accessibility generalizes).

### 3.3 Non-Goals

- **NOT** a real-time thread monitor (that's Orchestra Metronome).
- **NOT** a dev pipeline or CI/CD integration (that's Claude Clarified Code).
- **NOT** an AI-driven analysis that makes new claims about the thread (Analysis Layer — deferred; see Open Questions).
- **NOT** a multi-thread comparison or cross-thread diff tool (MVP = single export, single Clarity Corpus).
- **NOT** a replacement for the user's memory — it is a forensic reconstruction tool only.
- **NOT** integrated with the Anthropic API or direct session retrieval — MVP is file-in only.
- **NOT** a cloud-hosted service — MVP is local-only per data-sensitivity constraint.

## 4. User Journeys

### 4.1 Primary User Journeys

**Journey J1 — "What did Claude actually do?"**

- User goal: understand what happened in a thread whose chat summary feels incomplete or wrong.
- Steps: (1) User drops export zip onto landing surface. (2) Product parses and renders a timeline. (3) User sees chronologically-ordered events: user messages, assistant messages, tool uses, sub-agent spawns, thinking blocks, hook executions. (4) User clicks any event → detail view with full content.
- Outcome: user can answer "what did Claude do at step N?" for any N.
- Pain eliminated: guessing based on chat self-report; reading JSONL.

**Journey J2 — "Audit this claim"**

- User goal: verify a specific claim the agent made in-chat.
- Steps: (1) User has a specific question (e.g., "Did Claude actually run the convergence gate? Did it finish?"). (2) User drops the export zip, filters timeline by event type or sub-agent, or searches by keyword. (3) User navigates to the relevant events and reads actual content.
- Outcome: user can cite evidence for or against any claim the agent made in-thread.
- Pain eliminated: accepting the agent's self-report uncritically.

**Journey J3 — "Generate a shareable report"**

- User goal: produce a Clarity Corpus for sharing, citation, or personal record.
- Steps: (1) User finishes exploring a thread. (2) User clicks "Export Clarity Corpus." (3) Product generates the corpus: summary, timeline, per-type reports (tool uses, sub-agents, thinking, token accounting) in PDF + DOCX + XLSX (structured types) + MD. (4) User saves locally or shares.
- Outcome: a citable, accessible artifact the user owns.
- Pain eliminated: the "I saw it but can't prove it" problem; the research-citation problem.

### 4.2 Edge Case Journeys

**Journey E1 — Malformed export zip**

- User drops an incomplete or corrupted zip. Product renders what it can, flags missing components inline (e.g., "sub-agent acompact-* referenced but file not in zip — displayed as [unavailable]"), never crashes.

**Journey E2 — Very large export**

- User drops a 10,000+ line JSONL. Product shows loading indicator, streams rendering, remains keyboard-navigable during load, never blocks the UI.

**Journey E3 — Export with sensitive content the user didn't expect**

- Product detects patterns that look like API keys, credentials, or PII; surfaces a warning before export; never transmits anything.

## 6. Constraints

### 6.1 Business Constraints

- **Budget:** Free to build with current tooling. No paid infrastructure, no paid APIs, no cloud hosting fees. Source-session user statement: *"i am so broke i am deciding between food meds and gas."* This is a real constraint, not a preference.
- **Timeline:** MVP ship-target 2026-Q2, matched to D2R factorial-experiment cadence.
- **Organizational:** Single operator (Krystal) for MVP. No team-size dependencies. Hook orchestration + skill ecosystem per D2R required.

### 6.2 Regulatory Constraints

None binding at MVP. EU AI Act applicability (Article 50 transparency obligations for AI systems, Article 52 transparency for general-purpose AI model documentation) assessed in Stage 00 Track 2 research if/when product is distributed into EU. This PRD does not foreclose EU distribution.

### 6.3 Technical Constraints

- **Platform target:** Non-dev-accessible UI surface. Web app or desktop app — specific choice deferred to Stage 00 research, but the accessibility-first UI constraint is hard-locked. NOT CLI, NOT SDK, NOT dev-integrated.
- **Data sensitivity:** User-provided thread exports may contain personal data, accidentally-pasted API keys, client work, or Martinez Methods IP. **Data stays local to the user's machine. No cloud upload. No telemetry. No analytics.** This is a privacy constraint, not a product nicety.
- **IP discipline:** Per `feedback_ip_language.md` + `feedback_ip_discipline_filesystem.md`: no methodology exposure in product filenames, folder names, field values, or visible product strings. Martinez Methods branding. Convergence-gate and similar tooling described in branded terminology only.

### 6.4 Accessibility Constraints

**WCAG 2.1 AA minimum hardwired. Non-negotiable.**

Additional standards for this product (per user population):

- Screen-reader-first testing protocol (NVDA + Chrome, JAWS + Chrome, VoiceOver + Safari minimum).
- Keyboard-only operability on every path. No mouse-only interaction.
- `prefers-reduced-motion` honored on all animations.
- Color never the sole indicator of meaning.
- Contrast ratios: 4.5:1 (normal text), 3:1 (large text) minimum.
- Touch targets ≥ 44x44px on any touch-target surface.
- Cognitive accessibility: no gated sequencing that punishes non-linear navigation; every view reachable from every other view in ≤ 2 navigation steps.
