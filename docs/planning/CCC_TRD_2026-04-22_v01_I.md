## 2. Functional Requirements

### 2.1 Core Functional Requirements

| ID | Statement | Rationale | Acceptance Criteria | Priority |
|---|---|---|---|---|
| FR-001 | The system MUST ingest a Claude.ai thread export zip from the local filesystem. | Supports PRD J1/J2/J3 entry point | Drag-drop or file-picker yields a parsed thread in memory; no network call | Must |
| FR-002 | The system MUST parse the top-level JSONL event stream into structured events. | Core reconstruction data | Every JSONL line produces exactly one typed event object; zero event loss | Must |
| FR-003 | The system MUST parse all `subagents/*.jsonl` sub-agent transcripts and associate each to its `.meta.json`. | Surfaces sub-agent work per PRD Section 2.3 evidence item 1 | Every sub-agent file linked to its meta; orphaned files flagged, not discarded | Must |
| FR-004 | The system MUST parse all `tool-results/*.txt` files and associate each to its originating tool-use event. | Surfaces tool-result content buried in export | Every tool-result file linked by ID to a tool-use event in the timeline | Must |
| FR-005 | The system MUST parse `metadata.json` and surface session-level metadata (session ID, CLI session ID, cwd, model, created/last-activity timestamps, title). | Session context required for Clarity Corpus | All declared metadata fields rendered in session-info panel | Must |
| FR-006 | The system MUST render a chronologically-ordered timeline of all parsed events. | PRD J1 primary outcome | Timeline orders by timestamp ascending; ties broken deterministically | Must |
| FR-007 | The system MUST provide a detail view for any timeline event showing its full content. | PRD J1 step 4 | Clicking any timeline item reveals full content of that event | Must |
| FR-008 | The system MUST allow the user to filter the timeline by event type (user message, assistant message, tool-use, tool-result, sub-agent spawn, thinking block, hook execution). | PRD J2 navigation | Each event type filter togglable independently; filters compose | Must |
| FR-009 | The system MUST allow the user to search the timeline by keyword across event content. | PRD J2 search | Full-text search returns all matching events with hit highlighting | Must |
| FR-010 | The system MUST produce a token-accounting waterfall attributing token cost across main thread + sub-agents + tool uses. | PRD G2 | Waterfall sum ≥ 99% of declared total token count from metadata | Must |
| FR-011 | The system MUST export the Clarity Corpus to PDF. | PRD G3 | PDF generated contains timeline summary + per-type reports; passes PDF/UA accessibility check | Must |
| FR-012 | The system MUST export the Clarity Corpus to DOCX. | PRD G3 | DOCX opens in Word / LibreOffice / Google Docs without layout corruption | Must |
| FR-013 | The system MUST export structured data portions of the Clarity Corpus (tool-uses, sub-agents, token accounting) to XLSX. | PRD G3 (XLSX applies to structured-data types only) | XLSX contains typed columns; numeric cells are numeric-typed | Must |
| FR-014 | The system MUST export the Clarity Corpus to Markdown. | PRD G3 | MD file is well-formed CommonMark; renderable on GitHub | Must |
| FR-015 | The system MUST detect patterns matching common secret formats (API keys, AWS access keys, JWT, private keys, passwords) in event content and WARN the user before any export action. | Privacy constraint + edge case E3 | Detection ≥ 95% recall on a reference secret-pattern test set; pre-export modal blocks until acknowledged | Must |
| FR-016 | The system MUST degrade gracefully on malformed or incomplete export zips. | Edge case E1 | Missing components rendered as `[unavailable]` markers; no unhandled exceptions | Must |
| FR-017 | The system MUST parse `logs/*.log` files and surface them as a separate log panel. | Source session export includes logs/; completeness | Logs rendered in their own timeline-correlated panel | Should |

### 2.2 User-Facing Behavior Requirements

| ID | Description | Input/Trigger | Expected Output/Response | Timing |
|---|---|---|---|---|
| BR-001 | Drag-drop zip initiates ingest | File drop event on landing surface | Ingest begins; loading indicator visible within 100ms | Sync (perceptually) |
| BR-002 | Large-export streaming render | Ingest of JSONL > 1000 lines | Loading indicator + incremental timeline rendering; UI remains responsive | Async, ≤ 200ms per 100-line chunk |
| BR-003 | Keyboard navigation | Tab / Shift+Tab / Arrow keys / Enter | Focus moves predictably; every interactive element reachable; focus indicator visible | Sync, ≤ 16ms per keystroke |
| BR-004 | Inter-view navigation ≤ 2 steps | Any view + navigation action | Target view reachable in ≤ 2 navigation steps from any other view | Navigation steps counted deterministically |
| BR-005 | Pre-export secret warning | User initiates export + FR-015 detects pattern | Modal blocks export; lists detected pattern types + counts; requires explicit acknowledgement | Sync |
| BR-006 | prefers-reduced-motion honored | User system setting | Animations disabled or replaced with instant transitions | Sync |
| BR-007 | Screen-reader event announcements | Ingest progress, filter change, export completion | ARIA live region announces state change | Sync |

### 2.3 System-Facing Behavior Requirements

| ID | Description |
|---|---|
| SR-001 | Zip extraction runs in-memory or in a local sandboxed temp directory that is purged on app close; extraction path never leaves the user's machine. |
| SR-002 | Parse errors on any single event file produce a flagged `[unavailable]` marker but do not abort the overall ingest. |
| SR-003 | No telemetry, analytics, crash reporting, or network call SHALL originate from the running product. Hard-enforced by CI test + network-call static analysis. |
| SR-004 | Exports are written only to user-chosen local paths via OS file-picker. |

## 3. Non-Functional Requirements

### 3.1 Performance Requirements

| Metric | Target |
|---|---|
| Time-to-first-insight (zip-drop → timeline first render) | p50 ≤ 5s, p95 ≤ 10s, p99 ≤ 15s for 300-line JSONL |
| Clarity Corpus export (all 4 formats in parallel) | p50 ≤ 30s, p95 ≤ 60s, p99 ≤ 90s for 300-line JSONL |
| Streaming render throughput | ≥ 100 timeline events per 200ms chunk; UI interaction latency ≤ 100ms during streaming |
| Max supported JSONL size without UI block | 10,000 lines |
| Keystroke-to-focus-change latency | ≤ 16ms (60fps budget) |
| Search result latency | p95 ≤ 300ms for single-keyword search across 10,000 events |
| Memory ceiling (local app) | ≤ 500MB resident for 10,000-event export |
| Degradation beyond 10,000 events | Graceful slowdown with progress indicator; no hard refusal below 50,000 events |

### 3.2 Reliability Requirements

| Metric | Target |
|---|---|
| Crash rate per ingest | ≤ 1 per 1,000 ingests on reference test corpus |
| Parse-error recovery | 100% of single-file parse errors produce `[unavailable]` marker without aborting ingest (FR-016 + SR-002) |
| RTO (recovery time after crash) | User re-opens app and can re-ingest within 30s |
| RPO (data loss window) | Zero — source zip is untouched; all work is view-only until explicit export |
| Failure modes prohibited | Silent data loss; un-flagged missing events; export-side corruption of numeric fields |
| Failure modes tolerated | UI slowdown > 10,000 events (with progress indicator); parse-skip of individual malformed events (with `[unavailable]` marker) |

### 3.3 Security Requirements

| Field | Value |
|---|---|
| Authentication | None (local app, single-user model) |
| Authorization | None beyond OS file-access permissions |
| Data in transit encryption | N/A — no network calls at runtime (hard rule per SR-003) |
| Data at rest encryption | Inherits OS disk-level encryption; product does not add its own encryption layer at MVP |
| Secret management | N/A — no secrets stored by product; FR-015 detects secrets in user content for warning purposes |
| Audit logging | Local-only log of ingest/export events in user-controlled location; never transmitted |
| Applicable security standards | OWASP ASVS Level 1 (local-app relevant controls); CERT secure coding for implementation language (TBD Stage 00) |
| Threat model summary | Local-only threat model: risks are (1) reading sensitive content from user zips, addressed by FR-015 warning; (2) dependency supply chain, addressed by pinned dependencies + Stage QA audit; (3) zip-bomb / zip-slip, addressed by bounded extraction + path validation |

## 6. Technical Constraints

### 6.1 Mandatory Technology Choices

- **Local-only architecture:** application MUST run without any network connection (enforced by CI test + static analysis). No cloud services, no API calls at runtime.
- **WCAG 2.1 AA minimum:** UI framework + component library selected must support accessibility at this level without heroic effort.
- **Hook orchestration integrated (D2R):** Claude Code hooks + git hooks installed and operational per Section 6.4 below.
- **Skill/plugin ecosystem integrated (D2R):** per Section 6.5 below.

Specific language and framework selection deferred to Stage 00 Track 1 research (open question Q-001 in PRD).

### 6.2 Prohibited Technology Choices

- **No cloud/network services at runtime** (telemetry, analytics, crash reporting, CDN-loaded assets at runtime, external font services, external icon services, etc.). Hard rule.
- **No dynamic code execution on user-provided content.** The JavaScript-family function that interprets strings as code is prohibited from touching user content, as is any equivalent in other languages (Python `exec`, Ruby `instance_eval`, etc.).
- **No dependencies with known high-severity CVEs** unpatched at time of MVP ship (enforced at CI).
- **No native modules that require cloud build services** (build must be reproducible on user's local machine).

### 6.3 Platform Target

- **Non-dev-accessible UI surface** (web app or desktop app). Specific form-factor deferred to Stage 00 Track 1.
- **NOT CLI. NOT SDK. NOT dev-tool integration.** Per PRD Section 3.3 non-goals.
- Rationale: primary user segment is explicitly non-dev; secondary segment (researchers) tolerates GUI.

### 6.4 Hook Orchestration Requirements (D2R-Specific)

- **Claude Code hooks** (required in project's `.claude/settings.json`):
  - `PreToolUse` hook for ASAE Certainty Threshold enforcement before any file-write tool call
  - `PostToolUse` hook for build-time coverage floor enforcement
  - `Stop` hook to run convergence gate on stage-boundary artifacts
- **Git hooks** (required in `.githooks/`):
  - `pre-commit`: axe-core + coverage floor + secret scan + static type check
  - `pre-push`: full test suite + convergence gate on any modified planning docs
- **Convergence gate thresholds per stage (defaults per D2R):**
  - Stage 00: 2
  - Stage 01a: 2
  - Stage 01b: 3
  - Stage 02: 3
  - Stage 03+: 3
  - Stage QA: 5
  Severity policy default: `standard`. Any deviation must be declared + rationale-justified in TQCD Section 9.2.

### 6.5 Skill / Plugin Ecosystem Requirements

**Required (available during build):**

- `/dare-to-rise-code-plan`
- `/asae`
- `/ideate-to-d2r-ready` + its downstream write-* skills
- `/file-versioning`
- `/file-presentation`

**Beneficial (not required):**

- `/simplify` (for post-implementation cleanup)
- `/walk-me-through` (for explaining generated code to non-dev user)

**Excluded:**

- Any skill or plugin that initiates network calls from within the product build (violates SR-003).
